# Production Media Server Integration Guide

## Overview

This guide explains how to adapt the `push_av_stream` example to work with different production-grade media servers by making the ingest transport layer modular and configurable.

## Production Servers Compatible with CMAF/DASH Ingest

### 1. **MistServer** (Recommended for Open Source)
- **URL Pattern**: `https://server:port/stream_name/segment_0001.m4s`
- **Auth**: API key (`X-API-Key` header) or Basic Auth
- **Stream Creation**: Optional (implicit on first upload)
- **MPD**: Auto-generated or manual upload
- **Pros**: Simple API, good documentation, supports multiple output formats
- **Cons**: Requires server setup

### 2. **AWS Elemental MediaLive**
- **URL Pattern**: `https://ingest-endpoint.mediapackage.amazonaws.com/out/v1/{channel_id}/segment.m4s`
- **Auth**: AWS Signature V4 (requires AWS SDK or custom implementation)
- **Stream Creation**: Via AWS API (channel must be pre-created)
- **MPD**: Auto-generated by MediaPackage
- **Pros**: Scalable, cloud-native, CDN integration
- **Cons**: Complex authentication, requires AWS account

### 3. **Azure Media Services**
- **URL Pattern**: `https://{account}.mediaservices.windows.net/{streaming_locator}/segment.m4s`
- **Auth**: Azure AD token or API key
- **Stream Creation**: Via REST API
- **MPD**: Auto-generated
- **Pros**: Enterprise-grade, DRM support
- **Cons**: Complex setup, Azure-specific

### 4. **Wowza Streaming Engine**
- **URL Pattern**: `http://server:port/vod/stream_name/segment.m4s`
- **Auth**: API key or OAuth token
- **Stream Creation**: Via REST API (`/v2/servers/{server}/vhosts/{vhost}/applications/{app}/streams`)
- **MPD**: Auto-generated
- **Pros**: Industry standard, extensive features
- **Cons**: Commercial license required

### 5. **Generic DASH-IF Compliant Server**
- **URL Pattern**: Configurable via template
- **Auth**: Configurable (mTLS, API key, Basic Auth)
- **Stream Creation**: Configurable endpoint
- **MPD**: Manual upload
- **Pros**: Works with any DASH-IF compliant server
- **Cons**: Requires server-specific configuration

## Implementation Strategy

### Step 1: Refactor Current Code

The current `cmaf_push.c` is tightly coupled to Matter's push_av_server. To make it modular:

1. **Extract URL construction** into adapter functions
2. **Abstract authentication** into pluggable auth handlers
3. **Separate stream management** from segment upload
4. **Make content types configurable**

### Step 2: Create Adapter Interface

See `ingest_transport.h` for the abstract interface that all adapters must implement.

### Step 3: Implement Server-Specific Adapters

Each server gets its own adapter file:
- `matter_adapter.c` - Refactored from current `cmaf_push.c`
- `mistserver_adapter.c` - MistServer implementation
- `aws_adapter.c` - AWS MediaLive implementation
- `generic_adapter.c` - Configurable for any DASH-IF server

### Step 4: Configuration

Add Kconfig options to select server type:

```kconfig
choice INGEST_SERVER_TYPE
    prompt "Media server type"
    default INGEST_SERVER_MATTER

    config INGEST_SERVER_MATTER
        bool "Matter push_av_server"
    config INGEST_SERVER_MISTSERVER
        bool "MistServer"
    config INGEST_SERVER_GENERIC
        bool "Generic DASH-IF server"
endchoice
```

## Quick Start: MistServer Example

### 1. Install MistServer

```bash
# On your server
wget https://github.com/DDVTECH/mistserver/releases/download/...
# Follow MistServer installation instructions
```

### 2. Configure MistServer

Create a stream configuration that accepts CMAF push:

```xml
<Stream>
  <Name>esp32_stream</Name>
  <Source>push://</Source>
  <Output>cmaf://</Output>
</Stream>
```

### 3. Configure ESP32

In `menuconfig`:
- Set `INGEST_SERVER_TYPE` to `MistServer`
- Set `SERVER_HOST` to your MistServer IP
- Set `SERVER_PORT` to 443 (or your HTTPS port)
- Configure authentication (API key or Basic Auth)

### 4. Build and Flash

```bash
idf.py build flash monitor
```

## Migration Path

### Phase 1: Keep Current Implementation
- Rename `cmaf_push.c` → `matter_adapter.c`
- Wrap existing functions in adapter interface

### Phase 2: Add New Adapters
- Implement MistServer adapter (simplest)
- Test with MistServer
- Add other adapters as needed

### Phase 3: Refactor Main Application
- Update `push_av_stream_main.c` to use `ingest_transport_*` functions
- Remove direct calls to `cmaf_push_*` functions

## Benefits of Modular Design

1. **Flexibility**: Switch servers via configuration
2. **Testability**: Test with different servers easily
3. **Maintainability**: Server-specific code isolated
4. **Extensibility**: Add new servers without changing core code
5. **Standards Compliance**: Supports multiple DASH-IF interfaces
